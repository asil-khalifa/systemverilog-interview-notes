# Part 1: Randomization Basics

## 1.1 Introduction to Randomization

### In plain English

A directed test says "drive `a` = 200, `b` = 100, `op` = add, and expect 300". You write every value yourself. That is fine for ten cases and impossible for ten million. The 8-bit ALU alone has 256 × 256 × 8 = 524,288 input combinations, and a real design has vastly more.

Randomization turns the job around. Instead of listing the stimulus, you describe **what legal stimulus looks like** (the constraints), and the simulator generates as many different legal stimuli as you ask for. You then measure with functional coverage (Module 10) which interesting cases were actually hit.

### Technical definition

**Constrained-random verification** is a methodology in which stimulus is generated by a random number generator under the control of declarative **constraints**. In SystemVerilog the main mechanism is object-based: class properties are declared `rand` or `randc`, restrictions are written in `constraint` blocks, and the built-in `randomize()` method invokes the **constraint solver**, which assigns to all random properties a set of values that satisfies every active constraint.

### Why it is needed

| Directed testing | Constrained-random testing |
|---|---|
| Each test is written by hand | One test generates thousands of scenarios |
| Covers only what the engineer thought of | Also finds corner cases nobody thought of |
| Effort grows linearly with the number of scenarios | Effort is mostly up front (building the environment) |
| Progress is easy to see at first, then slows | Slow start, then coverage rises quickly |
| Expected results can be hard-coded | Needs a self-checking testbench (scoreboard) and functional coverage |
| Still needed for a few hard-to-reach cases | Used for the bulk of verification |

```text
   coverage
    100% |                                  _________  constrained-random
         |                         ________/        .
         |                  ______/             . '      directed
         |               __/               . '
         |             _/             . '
         |            /          . '
         |           /      . '
         |     _____/  . '
         |____/_ . '
         +---------------------------------------------> time
          ^ environment is being built: no results yet
```

Random stimulus alone is not enough. **Unconstrained** random values are mostly illegal (an opcode that does not exist, a packet length of four billion) or uninteresting. Constraints do two jobs:

1. **Legality:** generate only stimulus the DUT is specified to handle.
2. **Steering:** bias the stimulus toward interesting areas (boundaries, long bursts, error cases).

### The sources of random values in SystemVerilog

| Mechanism | Returns | Constraints | Typical use |
|---|---|---|---|
| `$random` | Signed 32-bit integer | None | Legacy Verilog. Avoid in new code |
| `$urandom` | Unsigned 32-bit integer | None | A quick random number in procedural code |
| `$urandom_range(max, min)` | Unsigned integer in [min, max] | Range only | Random delays, random counts |
| `obj.randomize()` | 1 (success) or 0 (failure); assigns the object's `rand`/`randc` properties | Constraint blocks and `with` | Transactions, configuration objects. The main mechanism |
| `std::randomize(v1, v2) with {...}` | 1 or 0; assigns the listed variables | Inline only | Randomizing local variables without a class |
| `randcase` | Chooses one branch by weight | Weights | Random choice between actions (Module 11) |
| `randsequence` | Generates a sequence from grammar rules | Weights | Structured random sequences (Module 11) |

### A first example

```systemverilog file=tb_rand_intro.sv
module tb_rand_intro;

  class simple_txn;
    rand bit [7:0] a;
    rand bit [7:0] b;

    constraint small_a_c { a < 10; }
  endclass

  simple_txn txn;

  initial begin
    txn = new();
    repeat (5) begin
      if (!txn.randomize()) $fatal(1, "randomize failed");
      $display("a=%0d b=%0d", txn.a, txn.b);
    end
    $display("$urandom_range(5, 1) = %0d", $urandom_range(5, 1));
  end

endmodule
```

**What to expect.** Five lines. In every line `a` is between 0 and 9 and `b` is anything from 0 to 255. The last line shows a number from 1 to 5. Sample output; actual values differ per seed and simulator:

```text
a=3 b=201
a=9 b=14
a=0 b=77
a=6 b=250
a=3 b=92
$urandom_range(5, 1) = 4
```

**Line by line**

| Line | Explanation |
|---|---|
| `class simple_txn;` | Random variables and constraints live in a class. Classes are covered in Module 4. |
| `rand bit [7:0] a;` | The keyword `rand` marks the property as a random variable. Without it, `randomize()` leaves the property alone. |
| `constraint small_a_c { a < 10; }` | A named constraint block. It contains one expression that must be true after randomization. |
| `txn = new();` | An object must exist before it can be randomized. Calling `randomize()` on a null handle is a run-time error. |
| `txn.randomize()` | Built-in method of every class. It calls the solver, assigns new values to `a` and `b`, and returns 1. It returns 0 if the constraints cannot be satisfied. |
| `if (!txn.randomize()) $fatal(...)` | The return value must always be checked. A failed randomization leaves the old values in place, and without the check the test continues with stale data. |
| `$urandom_range(5, 1)` | A random unsigned number between 1 and 5, both included. |

### How it works internally

A simulator contains a **pseudo-random number generator** (PRNG). It is deterministic: starting from the same **seed** it produces the same sequence of numbers. That is essential, because a failing random test must be reproducible by re-running it with the same seed.

```text
   seed --> PRNG --> raw random numbers --+
                                          v
   rand variables  ----------------->  constraint  ---> one solution ---> values written
   active constraints -------------->    solver                           into the object
   state variable values ----------->
```

The solver does not "generate a value and test it". It analyses the constraints as a whole, determines the set of legal solutions, and picks one of them. Section 2.1 describes this in detail.

> **Key point:** Randomization in a testbench is pseudo-random and repeatable. A regression runs the same test with many different seeds; when one fails, the seed is recorded and the failure is reproduced exactly with that seed.

### Interview questions

**Q1. What is constrained-random verification?**
A verification approach in which stimulus is generated randomly but restricted by constraints to legal and interesting values. Combined with a self-checking testbench and functional coverage, it reaches far more scenarios than hand-written directed tests.

**Q2. Why not use purely random stimulus?**
Most unconstrained values are illegal for the protocol or uninteresting. Constraints keep the stimulus legal and steer it toward corner cases.

**Q3. What is the difference between `$random` and `$urandom`?**
`$random` returns a signed 32-bit value and is the old Verilog function; its sequence is not managed per thread and object. `$urandom` returns an unsigned 32-bit value and takes part in SystemVerilog's random stability scheme, where every thread and object has its own generator (Section 4.5). New code uses `$urandom` or `$urandom_range`.

**Q4. If stimulus is random, how do you know what was tested?**
With functional coverage. Covergroups record which values and combinations occurred, so the random process is measured instead of assumed.

**Q5. How do you reproduce a failure found by a random test?**
Re-run the same test with the same seed, the same code and the same simulator version. The pseudo-random sequence is then identical.

## 1.2 rand and randc

### In plain English

Both keywords make a class property random. The difference is in how values repeat.

- `rand` is like **rolling a die**. Each roll is independent. You can get 4 three times in a row.
- `randc` is like **dealing cards from a shuffled deck**. You never see the same card twice until the whole deck has been dealt. Then the deck is reshuffled and dealing starts again.

### Technical definition

| Keyword | Definition |
|---|---|
| `rand` | Standard random variable. On each `randomize()` call the value is chosen with a **uniform distribution** over the values that satisfy the constraints. Successive calls are independent, so values may repeat at any time |
| `randc` | Random-**cyclic** variable. The solver iterates over all legal values in a random permutation. No value is repeated until every legal value has been produced once. Then a new permutation is started |

### Syntax

```systemverilog
class cfg;
  rand  bit [3:0] len;       // 0 to 15, may repeat
  randc bit [2:0] id;        // 0 to 7, each value once per cycle of 8
  rand  alu_op_e  op;        // enum: only the named values are generated
  randc bit [1:0] slot[4];   // array: each element is its own randc variable
  bit   [7:0]     fixed;     // not random: randomize() never changes it
endclass
```

### How randc works internally

```text
   randc bit [1:0] id;      legal values: 0 1 2 3

   cycle 1:   shuffle -> 2 0 3 1     calls 1 to 4 return 2, 0, 3, 1
   cycle 2:   shuffle -> 1 3 2 0     calls 5 to 8 return 1, 3, 2, 0
   cycle 3:   shuffle -> ...

   A value may appear twice in a row only across a cycle boundary
   (here: call 4 returns 1 and call 5 returns 1).
```

Rules that follow from this mechanism:

- The simulator must remember, **per object**, which values have already been used. That history belongs to the object. A new object starts a new cycle.
- `randc` variables are **solved before** all `rand` variables. The solver first picks the next cyclic value, then solves the remaining variables around it.
- If constraints restrict a `randc` variable, the cycle runs over the **constrained** set of values only.
- If the constraints on the variable change between calls, or none of the remaining values of the current permutation satisfies the constraints, the permutation is recomputed (the cycle restarts).
- Because the history must be stored, a tool may limit the size of a `randc` variable. The standard requires that at least 8 bits be supported; commercial simulators support more. Large `randc` variables cost memory and time.

### Restrictions on randc

| Restriction | Reason |
|---|---|
| Only integral types: `bit`/`logic` vectors and enums | A cycle needs a finite, enumerable set of values |
| Cannot appear in `solve`...`before` | `randc` variables are always solved first already |
| Cannot be the subject of a `dist` | A weighted distribution contradicts "each value exactly once per cycle" |
| Cannot have `soft` constraints | Soft constraints are defined only for `rand` variables |
| Cannot be declared for `std::randomize` | Local variables have no per-object history |

### Complete example

```systemverilog file=tb_rand_vs_randc.sv
module tb_rand_vs_randc;

  class dice;
    rand  bit [1:0] r;     // independent each time
    randc bit [1:0] c;     // cyclic
  endclass

  dice d;
  int  seen[4];            // how often each value of c was produced
  bit  ok;

  initial begin
    d = new();
    repeat (3) begin                      // three complete cycles
      seen = '{default: 0};
      repeat (4) begin
        if (!d.randomize()) $fatal(1, "randomize failed");
        $write("r=%0d c=%0d | ", d.r, d.c);
        seen[d.c]++;
      end
      ok = (seen[0] == 1) && (seen[1] == 1) && (seen[2] == 1) && (seen[3] == 1);
      $display(" every c value exactly once: %s", ok ? "yes" : "NO");
    end
  end

endmodule
```

**What to expect.** Three lines, each showing four randomizations. Within each line the four `c` values are a permutation of 0, 1, 2, 3, so every line ends with `yes`. The `r` values follow no such rule and will often repeat within a line. Sample output; actual values differ per seed and simulator:

```text
r=3 c=2 | r=3 c=0 | r=1 c=3 | r=0 c=1 |  every c value exactly once: yes
r=2 c=1 | r=2 c=3 | r=2 c=2 | r=0 c=0 |  every c value exactly once: yes
r=1 c=0 | r=3 c=2 | r=3 c=1 | r=1 c=3 |  every c value exactly once: yes
```

**Line by line**

| Line | Explanation |
|---|---|
| `rand bit [1:0] r;` | Four possible values, each with probability 1/4 on every call. |
| `randc bit [1:0] c;` | Four possible values, delivered as a shuffled permutation. |
| `int seen[4];` | A small histogram used to prove the cyclic property. |
| Outer `repeat (3)` | Because the first call starts the first cycle, calls 1 to 4, 5 to 8 and 9 to 12 are exactly three complete cycles. |
| `seen[d.c]++;` | Counts each value. |
| `ok = ...` | In a complete cycle every count must be exactly 1. |

### The classic randc bug: a new object every time

```systemverilog
// WRONG: randc has no effect
repeat (8) begin
  cfg c = new();                 // a brand-new object: its randc history is empty
  void'(c.randomize());
  $display("%0d", c.id);         // values repeat
end

// RIGHT: one object, randomized repeatedly
cfg c = new();
repeat (8) begin
  void'(c.randomize());
  $display("%0d", c.id);         // 8 different values
end
```

The cyclic history is stored in the object. In a generator that creates a new transaction object for every item (the normal style, see Module 9), a `randc` field in the transaction therefore does **not** cycle. The fix is to keep the `randc` variable in a long-lived object (the generator itself or a configuration object) and copy its value into each transaction, or to randomize one "blueprint" object repeatedly and send copies.

### rand versus randc

| Property | `rand` | `randc` |
|---|---|---|
| Meaning | Random | Random-cyclic |
| Repetition | A value can repeat at any time | No repeat until all legal values have been used |
| Distribution in one call | Uniform over the legal values | Uniform over the values not yet used in this cycle |
| History kept between calls | None | Yes, per object |
| Allowed types | Integral types, enums, packed structs, arrays, queues, object handles (and unpacked struct members declared `rand`) | Integral types and enums only (and arrays of them) |
| Size limit | None | Implementation-defined; at least 8 bits guaranteed |
| Solve order | Together with the other `rand` variables | Before all `rand` variables |
| `dist`, `soft`, `solve before` | Allowed | Not allowed |
| Cost | Low | Higher: history must be stored |
| Typical use | Data, addresses, lengths, delays | IDs, slots, ports, test-case selection, anything that should be visited exhaustively without repeats |

> **Interview trap:** "With `randc bit [1:0] x`, can the same value come twice in a row?" Yes, across a cycle boundary. The last value of one permutation can equal the first value of the next. `randc` guarantees no repetition *within* a cycle only.

> **Interview trap:** "Is the order of a `randc` cycle the same in every cycle?" No. A new random permutation is computed for each cycle.

> **Common mistake:** Using `randc` on a wide variable such as `randc bit [31:0] addr;`. The standard only guarantees 8 bits; tools that accept it need a great deal of memory or switch to an approximation. For "no repeated addresses" on wide values use a queue of used values and an `inside` constraint (Problem 10 in Part 5).

> **Verification application:** `randc` is used where each value should be exercised once before any is repeated: selecting which of 16 ports to drive, which register to access in a register sweep, which interrupt to raise, or which test scenario to run. It reaches full coverage of that variable in the minimum number of transactions.

### Interview questions

**Q1. What is the difference between `rand` and `randc`?**
`rand` chooses each value independently with a uniform distribution, so values can repeat. `randc` is cyclic: it goes through all legal values in a random order and repeats none until all have been used; then it starts a new random permutation.

**Q2. How many `randomize()` calls are needed to see all values of `randc bit [3:0] x`? Of `rand bit [3:0] x`?**
Exactly 16 for `randc`. For `rand` there is no guarantee; on average about 54 calls are needed to see all 16 values (the "coupon collector" result), and any particular run may need more.

**Q3. Can a `randc` variable have constraints?**
Yes. The cycle then covers only the values that satisfy the constraints. If the constraints change, the cycle is recomputed.

**Q4. Which is solved first, `rand` or `randc`?**
`randc` variables are solved first. As a consequence a `randc` value can be chosen that makes the remaining constraints unsatisfiable in cases where treating everything together would have found a solution.

**Q5. Why does `randc` not work when I create a new object for each transaction?**
The record of already-used values is stored inside the object. A new object has an empty record, so each call is the first call of a new cycle.

**Q6. Can a `real` or a `string` be declared `rand`?**
A `string` cannot. Up to IEEE 1800-2017 the standard solver handles integral types only, so `rand real` is not standard there; some simulators accept it as an extension and later revisions of the standard add real-valued random variables. In an interview, say "integral types only, tool support for reals varies".

**Q7. What values does a `rand` enum variable get?**
Only the named members of the enumeration, each with equal probability if there are no other constraints. The solver never produces an out-of-range enum value.

**Q8. What happens if a `rand logic [7:0]` variable is randomized?**
It receives two-state values only. The solver never generates X or Z.

## 1.3 The randomize() Method and Randomizing Class Properties

### Definition

Every class has a built-in method with this prototype:

```systemverilog
virtual function int randomize();
```

It cannot be overridden or redefined by the user. A call `obj.randomize()`:

1. finds new values for all active random variables of the object that satisfy all active constraints,
2. writes those values into the object,
3. returns **1** on success and **0** on failure.

### What randomize() does, step by step

```text
   obj.randomize()
        |
        v
   1. call obj.pre_randomize()               (and pre_randomize of rand member objects)
        |
        v
   2. collect:  - rand / randc variables whose rand_mode is ON
                - constraint blocks whose constraint_mode is ON
                - inline constraints from "with { ... }"
                - current values of all state variables
        |
        v
   3. solve:    - randc variables first
                - array sizes before array elements
                - arguments of functions called in constraints before their results
                - everything else simultaneously
        |
        +-----------------------------+
        | solution found              | no solution
        v                             v
   4. assign the new values       4. leave ALL variables unchanged
   5. call obj.post_randomize()   5. post_randomize() is NOT called
   6. return 1                    6. return 0   (most tools also print a message)
```

### Which properties are randomized

| Property | Randomized by `obj.randomize()`? |
|---|---|
| Declared `rand` or `randc`, with `rand_mode` on (the default) | Yes |
| Declared `rand`/`randc` but switched off with `rand_mode(0)` | No. It becomes a state variable |
| Not declared `rand` | No. It is a state variable; its current value is used in constraints |
| `rand` handle to another object, handle is not null | Yes: the solver also randomizes that object's random variables and applies that object's constraints, all in one solve |
| `rand` handle that is null | Skipped. The solver never creates objects |
| Non-`rand` handle to another object | Not randomized, even if that class has `rand` properties |
| `static rand` property | Yes; the one shared copy is randomized on every call from any object |

### Complete example

This example needs `alu_pkg.sv` from Module 1.

```systemverilog file=tb_randomize_basic.sv
module tb_randomize_basic;
  import alu_pkg::*;

  class alu_txn;
    rand bit [7:0]  a, b;
    rand alu_op_e   op;
    logic [8:0]     result;          // not random: filled in later by the monitor
    int unsigned    id;              // not random: a state variable

    constraint id_link_c { a >= id; }   // a state variable used in a constraint

    function void print(string tag = "");
      $display("%s id=%0d a=%0d b=%0d op=%s", tag, id, a, b, op.name());
    endfunction
  endclass

  alu_txn txn;
  int     status;

  initial begin
    txn = new();

    txn.id = 250;
    status = txn.randomize();
    $display("status=%0d", status);
    txn.print("[1]");

    txn.id = 300;                       // a (8 bits) can never be >= 300
    status = txn.randomize();
    $display("status=%0d", status);
    txn.print("[2]");
  end

endmodule
```

**What to expect.** The first call succeeds: `status=1`, and `a` is between 250 and 255. `b` is any 8-bit value and `op` is one of the eight named opcodes. The second call must fail: `status=0`, and the `[2]` line shows `id=300` with exactly the same `a`, `b` and `op` as the `[1]` line, because a failed `randomize()` leaves the random variables untouched. Most simulators also print a constraint-failure message. Sample output; the values of `a`, `b` and `op` differ per seed and simulator:

```text
status=1
[1] id=250 a=253 b=41 op=ALU_XOR
status=0
[2] id=300 a=253 b=41 op=ALU_XOR
```

**Line by line**

| Line | Explanation |
|---|---|
| `rand bit [7:0] a, b;` | Two random 8-bit fields. |
| `rand alu_op_e op;` | A random enum. Only `ALU_ADD` to `ALU_SHR` can be produced. |
| `logic [8:0] result;` | Not `rand`. It is the DUT's response and must never be randomized. |
| `int unsigned id;` | Not `rand`. Set by the generator. |
| `constraint id_link_c { a >= id; }` | `id` is a state variable. At the moment of the call its value (250, later 300) is read and treated as a constant. |
| First `randomize()` | The solver must find `a` in 250 to 255. Six values are legal. |
| `txn.id = 300;` | Now the constraint demands `a >= 300`, which an 8-bit variable cannot satisfy. |
| Second `randomize()` | No solution exists. The method returns 0 and writes nothing. |

### How to call randomize()

| Style | Verdict |
|---|---|
| `if (!txn.randomize()) $fatal(1, "randomize failed");` | Recommended. Always executes, always checks |
| `if (!txn.randomize()) $error(...);` | Fine when the test should continue |
| `assert (txn.randomize()) else $fatal(1, "...");` | Common, but risky: if assertions are disabled (for example with `$assertoff` or a simulator option), some tools do not evaluate the expression at all, so the object is **not randomized** |
| `void'(txn.randomize());` | Discards the status. Acceptable only in throwaway code |
| `txn.randomize();` | Calling a function and ignoring its result gives a warning in most tools, and failures go unnoticed |

> **Interview trap:** "What happens to the random variables when `randomize()` fails?" They keep their previous values. Nothing is partially assigned. `post_randomize()` is not called. Candidates often answer "they become 0" or "they become X".

> **Common mistake:** Forgetting `rand`. A property without `rand` is never changed by `randomize()`. If it is still mentioned in a constraint it acts as a constant, and a constraint such as `len < 10` with a non-random `len` of 0 is silently satisfied, or silently causes failures when `len` is 20.

> **Common mistake:** Randomizing a null handle. `alu_txn txn; txn.randomize();` is a null-object access. Call `new()` first.

### Interview questions

**Q1. What does `randomize()` return?**
An `int`: 1 if the solver found a solution and assigned it, 0 if the constraints cannot be satisfied.

**Q2. Can you override `randomize()`?**
No. It is a built-in virtual method. User code is added through the hooks `pre_randomize()` and `post_randomize()`.

**Q3. What is a state variable?**
Any variable used in a constraint that is not being randomized in this call: a non-`rand` property, a `rand` property whose `rand_mode` is off, or a variable from an enclosing scope. The solver reads its current value and treats it as a constant.

**Q4. Does `randomize()` create objects for `rand` handles?**
No. A `rand` handle that is null is skipped. If it is not null, the object it points to is randomized as part of the same solve.

**Q5. Why should the return value of `randomize()` be checked?**
On failure the old values stay in place and no error is raised by the language itself. Without a check, the testbench silently re-sends the previous transaction or uses uninitialised values.

**Q6. Why is `assert(obj.randomize())` discouraged?**
An immediate assertion can be switched off. In that case the expression inside it may not be evaluated, so the randomization does not happen and the test behaves differently with assertions on and off.

## 1.4 Randomizing Arrays

### In plain English

A packet has a payload of several bytes; a burst has several beats. Stimulus therefore often needs a random **collection** of values, and frequently the **number** of elements must be random as well. Declaring an array `rand` makes every element random. For dynamic arrays and queues the size can also be random.

### Rules by array type

| Array type | Declared `rand` means | Size |
|---|---|---|
| Fixed-size array `rand bit [7:0] d[4];` | Every element is randomized | Fixed |
| Dynamic array `rand bit [7:0] d[];` | Every element is randomized | Randomized **only if** `d.size()` appears in a constraint. Otherwise the current size is kept |
| Queue `rand bit [7:0] q[$];` | Same as a dynamic array | Same as a dynamic array |
| Associative array `rand int aa[string];` | The elements that already exist are randomized; keys are not created or changed | Not changed |
| Array of object handles `rand item it[];` | Each non-null element's object is randomized. Null elements are skipped; objects are never created | As above |

> **Key point:** If the size of a `rand` dynamic array or queue is not constrained, the array is **not resized**. An array that is empty before `randomize()` is still empty afterwards. This is the most common surprise with random arrays.

### How it works internally

```text
   rand bit [7:0] payload[];
   constraint len_c { payload.size() inside {[2:5]}; }

   Solve step 1:  payload.size()  is treated as a random variable -> say 4
   Solve step 2:  the array is resized to 4 elements
   Solve step 3:  payload[0..3] are random variables; foreach constraints are
                  expanded for exactly these 4 elements and solved
```

The size is always solved **before** the elements. This is an implicit ordering similar to `solve`...`before` (Section 3.3): a constraint on the elements cannot "push back" on the choice of size. If the size is chosen so that the element constraints cannot be met, randomization fails. Write size constraints that are safe by themselves.

### Syntax

```systemverilog
class pkt;
  rand bit [7:0] hdr[4];                 // fixed array
  rand bit [7:0] payload[];              // dynamic array
  rand int       gaps[$];                // queue

  constraint size_c {
    payload.size() inside {[1:8]};       // size is random, 1 to 8
    gaps.size() == payload.size();       // sizes can be related to each other
  }
  constraint value_c {
    foreach (payload[i]) payload[i] != 8'h00;      // constraint on every element
    foreach (gaps[i])    gaps[i] inside {[0:3]};
  }
endclass
```

`foreach` inside a constraint is covered in Section 2.5.

### Complete example

```systemverilog file=tb_rand_array.sv
module tb_rand_array;

  class pkt;
    rand bit [7:0] hdr[2];
    rand bit [7:0] payload[];
    rand bit [3:0] nosize[];             // size is never constrained

    constraint size_c  { payload.size() inside {[2:5]}; }
    constraint value_c { foreach (payload[i]) payload[i] inside {[8'h10:8'h1F]}; }
  endclass

  pkt p;

  initial begin
    p = new();
    $display("before : payload.size=%0d nosize.size=%0d", p.payload.size(), p.nosize.size());

    if (!p.randomize()) $fatal(1, "randomize failed");
    $display("after  : payload.size=%0d nosize.size=%0d", p.payload.size(), p.nosize.size());
    $display("hdr=%p payload=%p", p.hdr, p.payload);

    p.nosize = new[3];                   // give it a size by hand
    if (!p.randomize()) $fatal(1, "randomize failed");
    $display("again  : payload.size=%0d nosize.size=%0d nosize=%p",
             p.payload.size(), p.nosize.size(), p.nosize);
  end

endmodule
```

**What to expect.** The `before` line is exact: both sizes are 0. After the first randomization `payload.size` is between 2 and 5 and every payload element is between `10` and `1f` hexadecimal, while `nosize.size` is still 0 because its size is unconstrained. After `new[3]`, `nosize` keeps the size 3 and its three elements are random 4-bit values. Sample output; actual values differ per seed and simulator, and the layout printed by `%p` varies:

```text
before : payload.size=0 nosize.size=0
after  : payload.size=4 nosize.size=0
hdr='{'h3a, 'hc1} payload='{'h17, 'h10, 'h1e, 'h12}
again  : payload.size=2 nosize.size=3 nosize='{'h9, 'h0, 'hd}
```

**Line by line**

| Line | Explanation |
|---|---|
| `rand bit [7:0] hdr[2];` | Fixed array. Both elements are randomized on every call. |
| `rand bit [7:0] payload[];` | Dynamic array, initially empty. |
| `payload.size() inside {[2:5]};` | Makes the size random. The solver resizes the array. |
| `foreach (payload[i]) ...` | Applied to each of the elements that exist after the size has been chosen. |
| `rand bit [3:0] nosize[];` | No size constraint: the solver keeps whatever size the array has. |
| `p.nosize = new[3];` | The size is set procedurally. From now on three elements are randomized. |

### Always bound the size

```systemverilog
rand int data[];
constraint bad_c  { data.size() > 0; }             // upper bound: about 2 billion elements
constraint good_c { data.size() inside {[1:64]}; } // always give an upper bound
```

With only a lower bound, the solver is free to choose a size in the millions. The simulation then appears to hang or runs out of memory. Always constrain a random size from both sides.

### Arrays of objects

```systemverilog file=tb_rand_obj_array.sv
module tb_rand_obj_array;

  class beat;
    rand bit [7:0] data;
    constraint c { data inside {[1:9]}; }
  endclass

  class burst;
    rand beat beats[];                       // array of handles

    function new(int n);
      beats = new[n];
      foreach (beats[i]) beats[i] = new();   // the objects must be constructed by hand
    endfunction
  endclass

  burst b;

  initial begin
    b = new(3);
    if (!b.randomize()) $fatal(1, "randomize failed");
    foreach (b.beats[i]) $display("beat %0d: data=%0d", i, b.beats[i].data);
  end

endmodule
```

**What to expect.** Three lines, `beat 0` to `beat 2`, each with `data` between 1 and 9.

The array holds handles. `rand` on the array means "randomize the objects these handles point to". The solver never calls `new()`. If the size were constrained and the solver enlarged the array, the new elements would be null handles and would simply be skipped. The standard pattern is therefore: allocate the maximum number of objects in the constructor or in `pre_randomize()`, and constrain a separate `rand int n_beats` that says how many of them are used.

### Multidimensional arrays

```systemverilog file=tb_rand_2d.sv
module tb_rand_2d;

  class grid;
    rand bit [3:0] m[3][4];                 // fixed 3 x 4
    rand int       d[][];                   // dynamic rows of dynamic columns

    constraint m_c {
      foreach (m[i, j]) m[i][j] inside {[1:9]};
    }
    constraint d_size_c {
      d.size() == 2;                        // number of rows
      foreach (d[i]) d[i].size() inside {[1:3]};   // length of each row
    }
    constraint d_val_c {
      foreach (d[i, j]) d[i][j] inside {[100:109]};
    }
  endclass

  grid g;

  initial begin
    g = new();
    if (!g.randomize()) $fatal(1, "randomize failed");
    foreach (g.m[i]) $display("m[%0d] = %p", i, g.m[i]);
    foreach (g.d[i]) $display("d[%0d] = %p", i, g.d[i]);
  end

endmodule
```

**What to expect.** Three lines `m[0]` to `m[2]`, each a row of four values between 1 and 9. Then exactly two lines `d[0]` and `d[1]`, each with one to three values between 100 and 109; the two rows may have different lengths.

**Line by line**

| Line | Explanation |
|---|---|
| `rand bit [3:0] m[3][4];` | Twelve random elements. |
| `foreach (m[i, j])` | One `foreach` with two loop variables visits every element of a two-dimensional array. Note the syntax: `m[i, j]` in the `foreach` header, `m[i][j]` in the body. |
| `rand int d[][];` | A dynamic array of dynamic arrays: a "jagged" array whose rows can differ in length. |
| `d.size() == 2;` | Size of the first dimension. |
| `foreach (d[i]) d[i].size() inside {[1:3]};` | Size of each row. Each row size is its own random variable. |
| `foreach (d[i, j]) ...` | Element constraints, expanded after all sizes are known. |

> **Note:** Constraining the sizes of a multidimensional dynamic array as shown is supported by the major commercial simulators, but it is one of the areas where tool behaviour has differed between versions. If a tool rejects it, allocate the array in `pre_randomize()` using separately randomized size variables.

### Common mistakes

> **Common mistake:** Expecting an unconstrained-size dynamic array to receive a random size. It keeps its current size; an empty array stays empty.

> **Common mistake:** Writing a constraint on `payload[0]` when the size may be 0. If the solver picks size 0, the index is out of range and the randomization fails or reports an error. Guard it: `payload.size() > 0 -> payload[0] == 8'hA5;` or make the minimum size 1.

> **Common mistake:** Declaring `rand item arr[];` and expecting the solver to create the `item` objects. It does not.

> **Verification application:** A packet class typically has `rand bit [7:0] payload[];` with `payload.size()` constrained to the legal packet lengths, a `dist` on the size to favour minimum and maximum lengths, and a `crc` field computed from the payload in `post_randomize()`.

### Interview questions

**Q1. How do you randomize the size of a dynamic array?**
Declare the array `rand` and constrain `arr.size()`, for example `arr.size() inside {[1:10]};`. The solver chooses the size first, resizes the array, then randomizes the elements.

**Q2. What happens if a `rand` dynamic array has no size constraint?**
Its size is left unchanged. The existing elements are randomized. If the array is empty, nothing happens.

**Q3. Which is solved first, the size of an array or its elements?**
The size. Element constraints are then expanded for that size.

**Q4. How are the elements of a `rand` associative array randomized?**
Only the entries that already exist are randomized. No keys are added or removed.

**Q5. How do you randomize an array of class objects?**
Declare the array of handles `rand`, construct every object before calling `randomize()` (in the constructor or in `pre_randomize()`), and then randomize the containing object. The solver randomizes each non-null element and never constructs objects.

**Q6. How do you constrain each element of a two-dimensional array?**
With a `foreach` that has one loop variable per dimension: `foreach (m[i, j]) m[i][j] < 10;`.

**Q7. Why must a random array size have an upper bound?**
Without one, the solver may choose a very large size, consuming memory and time. A size constraint such as `size() > 0` permits sizes up to the maximum of a 32-bit integer.
